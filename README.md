# qxfly-image-host · 多云端图床管理

一套「一次上传，多端可用」的图床管理系统。同一份 Vue 3 前端既可作为**浏览器端**部署，也可打包成 **Tauri 2 桌面客户端**；后端为 Spring Boot 3 + MySQL，通过统一的存储 SPI 屏蔽 9 种存储后端的差异（含把图片直接存在服务器本机磁盘的「本地存储」）。

除数据库外，**运行所需环境全部随包自带**（```runtime/``` 目录下的便携 JDK 与 Node），目标机器不需要预装 Java、Node，也不需要联网。

```powershell

## 二、数据库：注册成服务 + cmd 可控 + 开机自启

MySQL 默认安装在 ```C:Program FilesMySQLMySQL Server 8.0```。项目提供的 ```mysql-service.cmd``` 会：

- 自动从已有服务 / 常见目录探测 MySQL 安装位置
- **注册 Windows 服务**（已存在则跳过），设置 ```start= auto``` 开机自启，并配置异常自动重启
- 把 ```bin``` 目录写进 PATH，**让 cmd 里能直接敲 mysql**
- 初始化业务库与专用账号，把连接信息写进 ```configlocal.env```（start 脚本会自动读取）

```cmd
mysql-service.cmd status                          :: 查看服务状态 / 端口 / PATH / 连接测试
mysql-service.cmd install                         :: 注册服务 + 开机自启（需要时会请求 UAC 提权）
mysql-service.cmd start | stop | restart
mysql-service.cmd autostart on | off
mysql-service.cmd path add | machine | remove     :: add 写用户 PATH，machine 写系统 PATH
mysql-service.cmd init -User root -Password 密码   :: 建库建账号并写 configlocal.env
mysql-service.cmd console                         :: 打开 mysql 命令行
```:: 项目根目录里还有一个 mysql 客户端入口，无需改 PATH 也能直接用：
mysql --version
mysql -uroot -p -e "show databases;"
```

同一套能力在 Ubuntu 上是 ```./mysql.sh```：

```bash
sudo ./mysql.sh install            # apt 安装 + systemctl enable --now
./mysql.sh status
./mysql.sh autostart on
./mysql.sh init -u root -p 密码
```

### 连接信息放在哪

```mysql-service.cmd init``` 会创建业务库 ```qxfly-image-host``` 与独立账号（随机口令），并写入：

```text
config/local.env
  MYSQL_HOST / MYSQL_PORT / MYSQL_DATABASE / MYSQL_USER / MYSQL_PASSWORD
```

```start.cmd``` / ```start.sh``` 启动时会自动加载它。该文件已被 ```.gitignore``` 忽略。
没有它时会退回到 ```application.yml``` 里的默认口令（root / qxfly-image-host123），连不上还会自动降级到 H2 内存库，保证一键可用。

### 本地存储（存在服务器本机磁盘）

所有图片都落在**运行后端的这台机器**上，不依赖任何第三方服务、不需要任何密钥、也不受外网限制；
适合自建服务器、NAS、家里的小主机，或者只是想先跑起来试试的场景（它是类型列表里的第一项）。

配置只有三项：

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| 存储目录 | ```uploads``` | 绝对路径（如 ```D:\images```、```/data/images```）或相对服务进程工作目录的路径；不存在会自动创建 |
| 对外访问前缀 | 空 | 留空则自动用**你访问本服务所用的地址**；放在 Nginx / CDN 后面时填外部地址，例如 ```https://img.example.com``` |
| 路径前缀 | ```images``` | 图片在存储目录里的子目录 |

工作方式：

- **写入**：`<存储目录>/<路径前缀>/yyyy/MM/dd/[{分片}/]{uuid}.{ext}`；先写临时文件再原子改名，不会留下半截图片
- **访问**：由本服务的 `GET /files/{配置ID}/{对象键}` 直接把文件读出来（带 `Cache-Control`，浏览器会缓存）。
  图片直链就是这个地址，**匿名可访问** —— 浏览器的 `<img src>` 带不上 JWT，其他后端（GitHub raw / OSS 等）的直链同样是公开的；
  对象键里有随机 uuid，猜不到
- **回收站**：逻辑删除时在磁盘上把文件改名到 `_trash/` 下（**同一块盘，零流量**），恢复时再改回来；
  彻底删除才真正删掉，并顺手清掉空的日期目录
- **下载**：后端直接读磁盘，不走网络（私有仓库那种「拉不到直链」的问题在这里不存在）
- **从存储导入**：直接扫描存储目录，已有的图片也能登记进来
- **批量迁移**：可以作为源或目标，与其他后端互相搬家
- 环境变量：```LOCAL_STORAGE_DIR```（默认目录）、```LOCAL_STORAGE_PUBLIC_URL```（对外前缀），
  也可以在「存储设置」里为每个配置各填一份

> 换机器 / 换容器时，存储目录要跟着挂载或迁移，否则图片会「找不到」；
> 目录别放在会被清理的临时目录里（默认的 ```server/uploads``` 已被 .gitignore 忽略）。

### 图库筛选（体积 / 日期 / 尺寸）

工具栏的「**筛选**」按钮（右上角有生效维度数量的角标）支持按区间过滤，未填的维度不参与：

- **体积**：最小 / 最大，单位 MB（实测 4980 张里筛 1MB 以上 = 1368 张）
- **上传日期**：起止日期，含当天（左闭右开）
- **宽 / 高**：像素区间（导入的旧图没有尺寸记录，不会被命中）
- 与关键字、目录、存储后端**可叠加**；「重置」一键清空

接口：`GET /api/images?minSize=&maxSize=&dateFrom=&dateTo=&minWidth=&maxWidth=&minHeight=&maxHeight=`，
全部可选。后端查询对象为 `ImageQueryDTO`，后续加筛选维度只需加字段。

### 从仓库/桶导入已有图片

仓库或存储桶里**原本就存在**的图片（别处传的、或接入平台之前传的），可以在「图库 → 从存储导入」里扫出来并批量登记进平台：

- **全量拉取，不受条数限制**：GitHub 先用 `git/trees?recursive=1` 一次拿整棵树；仓库太大被截断（返回 `truncated=true`）时，会自动退化成「逐级遍历子树」继续拉，直到取完。S3 兼容存储用 `ListObjectsV2` 的 continuation token 翻页续拉。`IMPORT_MAX_FILES`（默认 20000）只作为内存保护上限
- 扫描结果按页返回（每页 200 条），界面可选「导入选中」或「全部导入」；「全部导入」由服务端自己遍历，不受分页影响
- 导入只登记元数据（对象键、大小、访问地址），**不会重新下载或上传文件**；导入的记录没有 sha256 与宽高，因此不参与秒传
- 已导入的文件会标记出来并自动跳过，重复导入不会产生重复记录
- SM.MS / ImgBB 没有列举接口，界面会直接禁用并提示
- 其余类型（阿里云 OSS / 腾讯云 COS / 七牛云）要支持导入，只需实现 `StorageService.list()` 一个方法

### 上传路径与目录分片

上传的对象键形如：

```text
{pathPrefix}/{yyyy}/{MM}/{dd}/{NNN}/{uuid}.{ext}
```

`NNN` 是分片目录，从 `001` 开始编号。同一个存储后端当天每写满 `UPLOAD_SHARD_SIZE`（默认 500）个文件，就自动换到下一个分片目录，
这样单个目录不会堆积成千上万个文件（GitHub 网页端和 Contents API 在目录超过 1000 个文件时都会很难受）。

把 `UPLOAD_SHARD_SIZE` 设为 0 可关闭分片，回到 `{pathPrefix}/{yyyy}/{MM}/{dd}/{uuid}.{ext}` 的老结构。

> **分片规则**：只在「最后一个分片」上继续填，填满 `UPLOAD_SHARD_SIZE` 才顺延到下一个（001 → 002 → …），
> 所以正常情况下任何分片都不会超过这个上限。分配是原子的（进程内槽位 + 加锁），并发上传不会撞到同一个位置；
> 槽位首次使用时从数据库恢复，重启后不会覆盖已有分片。自定义子目录（例如「保留原目录结构」迁移过来的 `holiday/`）不参与分片计数。
>
> 注意：**从存储导入**和**保留了原目录结构的迁移**会原样保留远端的对象键，不经过分片逻辑，
> 所以它们可能往同一个目录里放超过 500 个文件。要把已有目录重新分片，对它做一次「不保留目录结构」的迁移即可。

### 单张文件大小上限（可改，且支持无上限）

入口：**左侧菜单 → 系统设置**（仅超级管理员）。打开**「无上限」**后单张文件想传多大就传多大。

- **立即生效，不用重启**：上限存在数据库里，改完下一次上传就按新值判断
- **无上限是字面意思**：服务端 Servlet 层的 multipart 硬上限默认也放开了
  （```spring.servlet.multipart.max-file-size: -1```），限制只在应用层判断
- **服务端兜底**：如果担心有人拿"无上限"灌磁盘，用环境变量 ```UPLOAD_SERVLET_MAX``` 给一个硬上限
  （例如 ```UPLOAD_SERVLET_MAX=2GB```），这样超过的值在进业务代码之前就被拒掉
- **浏览器端也会先拦一道**：上传页按同一份上限做预校验，超限的文件直接提示、不会白传一遍
- 校验顺序：先看 `MultipartFile.getSize()` 再读内容，所以超大文件不会先把内存撑爆
- 出厂默认值是 ```app.upload.max-size```（```UPLOAD_MAX_SIZE```，30MB）；
  数据库里的系统设置一旦存在就以它为准（清掉 ```app_setting``` 表里那一行即可回到默认值）

> 设成"无上限"时，真正的边界变成：磁盘剩余空间、HTTP 超时、以及目标存储后端自己的限制。
> 例如 GitHub 的 Contents API 走 Base64 JSON，超大文件耗时会明显变长（实测 40MB 可正常上传）。

### 仓库目录整理（临时工具）

「个人中心 → 临时工具 → 仓库目录整理」。把 GitHub 仓库某个目录下的图片文件按系统存储规则搬到另一个目录，
例如把 `api/` 下平铺的图片收进 `api/images/`。

- **只支持 GitHub**：同仓库移动不需要搬运内容
- **不重新下载上传**：GitHub 的 Git Data API 允许新 tree 直接引用**原有 blob 的 SHA**，
  所以整个过程只要 6 次左右的 API 调用、**一个提交**就能搬完任意数量的文件
  （对比通用批量迁移：4107 个文件要 1.2 万次调用、约 2.5 小时，还会留下 4107 个提交）
- **默认只换目录、不改名**：`api/a.png` → `api/images/a.png`
- 可选「按 日期/分片 分层」：变成 `api/images/2026/10/13/001/a.png`；
  也可以关掉「保留原文件名」改用 uuid（就是普通上传的命名方式）
- **重名不覆盖**：保留原文件名时，如果目标位置已经有同名文件，那个文件会被**跳过并单独列出来**，
  预览和执行结果里都会显示数量与具体路径 —— 不会静默覆盖掉已有文件
- 默认只处理**直接放在源目录下**的文件，子文件夹里的不动；勾选「包含子目录」才递归
- 非图片文件按扩展名自动跳过
- **目录写法很宽容**：`api`、`/api/`、`main/api`、`owner/repo/main/api`、
  `https://github.com/owner/repo/tree/main/api` 都会被解析成同一个 `api/`（分支名会被自动去掉）
- **执行前建议先点「自检」**：逐项验证 Token、写权限、分支、最近提交、文件树、配额、以及本次能匹配到多少个文件，
  全只读。排查"执行了但没动静"就看这里
- **没有可移动文件时执行会直接报错**，不会静默成功；已有的同名文件只会被跳过并列出来
- **大批量建议分批搬**：请求里带 `maxFiles`（例如 500）就只搬这么多，搬完立刻提交。
  搬走的文件不再匹配源目录，所以反复执行会自然往下推进，不需要记录进度；中途失败也只损失这一批，
  前面的都已提交。实测 4979 个文件分 10 批、约 17 分钟搬完
- **GitHub 的 tree 接口对大批量不友好**：实测一次提交 1000 个文件（2000 条 tree 记录）会返回
  `502 Server Error` 或 `422 "your request timed out"`，甚至出现**返回 200 但响应体里没有 sha**。
  工具内置了重试，并且会校验拿到的 sha 是不是 40 位十六进制（只看 HTTP 状态码不够）
- 点「预览」可以先看清楚会移动多少个、分片怎么分布、路径长什么样（预览不会占用分片号）
- 执行后会同步更新图库记录的 `objectKey` / `url`；仓库历史里多一个提交，可以用 `git revert` 回退

实测（保留原名 + 不分层）：桩里 `api/a.png`、`api/b.jpg`、`api/c.gif`、`api/readme.txt`、`api/sub/x.png`，
目标目录里预先放了一个同名的 `api/images/a.png`：

- 命中 2 个（`readme.txt` 不是图片、`sub/` 是子目录，都不算）
- `a.png` 因为 `api/images/a.png` 已存在被跳过并列出，**没有覆盖**
- `b.jpg` → `api/images/b.jpg`、`c.gif` → `api/images/c.gif`，文件名原样保留
- tree 只有 4 条记录（2 个新增引用原 blob + 2 个删除），1 个提交

勾上「按 日期/分片 分层」后路径变成 `api/images/2026/10/13/001/a.png`，因为路径不同就不再有重名问题。

### 仓库重复文件清理（临时工具）

清理仓库里同名的重复图片：同名（含 `-1` / `-2` 这类数字后缀）只保留一份，其余删掉。

- **同名不等于同内容，所以不能只看文件名**：判断前会比对每个文件的 blob SHA
  - 内容相同 → 真重复，安全删除
  - 内容不同 → 同名但其实是两张不同的图，**默认不删**，只在结果里列出来
- **只认 `-1` ~ `-99`（1~2 位数字）后缀**，`(1)`、`(2)` 这类名字完全不动；
  `foo-2024.png` 这种年份后缀也不会被误判
- 后缀会**反复剥离**：`foo-1-1.png` 归到 `foo.png` 那一组
- 带 `-N` 后缀但**找不到同名基名**的（可能是唯一的图）默认不删，单独列出
- 每组的保留项**优先选图库里有记录的那一份**，删掉的记录会把库里的行改写过去或清掉，
  所以清理完图库不会出现指向已删文件的坏记录
- 预览（只读）与执行分开，先用预览看清楚再执行

> 实测：6255 个图片里有 872 组重名、全部内容一致，删掉 1256 个；随后发现 `-1-1` 叠加后缀漏网，
> 修正后补删 19 个。两次共清理 1275 个重复文件，仓库 9 个提交，图库记录同步无残留。

### 图库搜索

搜索框前可以切换 **模糊** / **精准** / **目录** 三种模式：

| 模式 | 匹配方式 | 典型用法 |
| --- | --- | --- |
| **模糊**（默认） | 文件名或对象键**包含**关键字 | 记得一部分，找找看 |
| **精准** | 文件名或对象键与关键字**完全相等** | 粘贴一个完整对象键定位某一张图 |
| **目录** | 对象键或文件名**以关键字开头** | 粘贴一个目录路径，列出它下面的所有图 |

- 关键字里的**前导斜杠会被自动忽略**（对象键是相对路径，不以 `/` 开头），
  所以 `/api/images/2026/10/12/002` 和 `api/images/2026/10/12/002` 效果一样
- 「目录」模式填短一点也行：`api/images/2026/10/12/00` 会把 `001` 和 `002` 一起列出来
- 搜不到结果时，空状态会提示当前模式为什么没匹配上（比如用「精准」搜目录）
- 搜索可以和目录筛选、存储后端筛选叠加使用

### 目录树

图库左侧是按 `object_key` 聚合出的目录树，点节点即可只看该目录（**含子目录**），每个节点显示文件数；
图片卡片上也会直接标出它所在的目录。

- `GET /api/images/directories` 返回嵌套结构 + 每层文件数，父目录的数字含所有子目录
- 直接放在根目录（对象键里没有斜杠）的散图归到「（根目录）」节点
- 目录不单独存字段，每次按对象键实时聚合，所以上传 / 导入 / 迁移后立刻就对

### 图片缓存

图库缩略图会缓存到浏览器本地（IndexedDB），**再次进入图库不会重新下载**：

1. 缩略图进入视口才取图（提前 200px 预取），不会一次性下载整页
2. 命中缓存且距上次校验不足 30 分钟 → 直接用缓存，**零网络请求**
3. 超过 30 分钟 → 带 `If-None-Match` / `If-Modified-Since` 做条件请求
   - 服务端回 `304` → 内容没变，复用缓存（省掉整个响应体）
   - 回 `200` 但 `ETag` 与缓存一致 → 同样复用，连响应体都不读
   - `ETag` 变了 → 替换缓存
4. 取不到内容（多为对方 CDN 未开 CORS）→ 自动回退成直接用原图地址，行为与没做缓存时一致；
   同一台主机失败过一次就记住，不会每张图都白发一次请求
5. 同一地址的并发请求会合并成一次

缓存最多 3000 张，超出后淘汰最久未校验的。在「个人中心 → 本地图片缓存」可查看占用并一键清空。

### 图库分页

图库每页条数可选 **30 / 50 / 100 / 200**，也可以选「自定义」直接填整数（1 - 500，超过按 500 处理）。
选择会记在浏览器里，下次打开还是这个值。

### 图片下载

图库里的图片可以直接下载，不用再去翻存储后端：

- **单张下载**：图片卡片上的「下载」按钮，存下来的文件名就是上传时的原始文件名
- **批量下载**：工具栏「批量下载」→「下载选中（N 张）」或「下载本页（N 张）」，
  服务端打包成一个 zip 回传，一次最多 500 张
- **走服务端代理，不走存储直链**：浏览器直接访问直链既带不上 JWT，私有仓库 / 私有桶的地址也拿不到内容，
  所以由后端按「对象键优先、直链兜底」读回字节再回传，私有存储同样能下载
- **边取边写**：zip 是流式生成的，内存里最多只放一张图，几百张也不会把服务端撑爆
- **单张失败不毁整包**：某张取不回来时跳过它，并在包内的 `下载失败清单.txt` 里列出原因
- **不会悄悄少图**：勾选的图片里只要有一张不存在 / 不属于你，整包都不生成并直接报错；
  包内重名文件自动追加 `-1`、`-2`，不会互相覆盖

### 上传会话与实时列表

上传不是"一次请求等结果"，而是一个跟着标签页走的**上传会话**：

- **加进列表就开始传**：拖拽 / 选择 / 粘贴的图片会**立刻**出现在上传列表里（排队中 → 上传中），
  不是等传完才显示
- **实时进度**：每张显示进度条、**速度**、**预计剩余时间**、状态（排队 / 上传 / 完成 / 失败 / 已取消）；
  顶部还有整体进度、总速度与总剩余时间
- **切页面不中断**：上传跑在 Pinia store 里、浮层挂在布局上，
  所以切到图库 / 概览 / 设置都照常上传，右下角一直有个小面板显示"上传中 N 张 · 总速度 · 剩余"
- **状态持久化到 sessionStorage**（绑定标签页会话，不是路由）：
  刷新页面列表和进度都还在，**多开标签页互不干扰**，关掉标签页就自然清空。
  注意浏览器的 File 句柄存不进 sessionStorage，所以刷新后正在传的那几张会标记为「已中断」，重新添加即可
- **并发 2 张**（太高会互相抢带宽、进度和 ETA 也不准）；**GitHub 后端在服务端会把同一个仓库分支的写操作串行化**
  —— Contents API 每上传一个文件就要提交一次，并发提交必然有一个撞 409
  （`is at xxx but expected yyy`），串行化后 8 张并发实测 8/8 成功、0 冲突；
  同一把锁也覆盖仓库目录整理 / 回收站搬运，避免它们更新分支引用时被并发上传顶掉
- 失败 / 取消的可以**重试**（文件还在内存里时），
  有任务在传时关闭标签页浏览器会提示确认
- 单张请求走的是 `POST /api/images/upload`，逐张上传才能拿到每张的进度

### 缩略图（按需生成 + 磁盘缓存）

图库列表加载的**不是原图**：没有原生缩略图的后端（GitHub / 对象存储 / 本地存储）会拿到一个按需缩略图地址。

- 地址形如 ```/thumb/{id}?w=400&s=签名```，**带 HMAC 签名**：缩略图端点要匿名可访问（`<img>` 带不上 JWT），
  而图片 id 是连续自增的，不签名就等于把全站图片暴露成可枚举资源
- 首次访问时缩放并写入磁盘缓存，之后直接命中（缓存目录 ```THUMB_CACHE_DIR```，默认 ```server/thumbs```）；
  原图内容指纹进了缓存文件名，换图自动失效
- 宽度可用 ```?w=``` 指定（32 ~ 1600，默认 400）；带透明通道输出 PNG，其余输出 JPEG
- **解不了的格式**（SVG / WebP）与**超过 ```THUMB_MAX_SOURCE```（默认 20MB）的原图**直接返回 404，前端自动退回原图地址
- 回收站里的图不生成缩略图
- **缓存有上限与保留期**：超过 `THUMB_CACHE_MAX_SIZE`（默认 2GB）按最久未使用淘汰、
  超过 `THUMB_CACHE_DAYS`（默认 30 天）按时间清理；每写 50 张惰性触发一次，
  「系统设置 → 缩略图缓存」可查看占用并一键清空（只删缓存，不影响原图与图库记录）
- **地址是绝对的**（' + F + 'http://你的地址/thumb/...' + F + '）：页面不一定来自后端本身 —— Tauri 桌面端页面来自 ' + F + 'tauri://localhost' + F + '、
  Vite 开发服务器只代理 /api、反向代理挂在别的域名下，根相对地址（' + F + '/thumb/...' + F + '）在那些场景全都打不开。
  基地址的取值顺序：**当前请求地址 → ' + F + 'PUBLIC_BASE_URL' + F + ' → ' + F + 'http://127.0.0.1:<端口>' + F + '**
- 同理，**本地存储的直链在读的时候会按当前请求地址重拼**：换了端口 / 域名 / 反向代理之后，
  老记录里存的上传时地址（例如 ```http://127.0.0.1:8082/files/...```）依然能打开，不用重新上传；
  如果配置里显式写了「对外访问前缀」，那就以配置为准

### 分享链接（相册）

在**图库**里勾选图片 → 「分享」→ 设置标题 / 访问密码 / 有效期 → 创建并复制链接，形如 ```https://你的域名/#/s/{token}```。

- **匿名可访问**：拿到链接的人不用登录；需要密码的相册在 ```POST /api/shares/{token}/view``` 校验密码（BCrypt 存储）
- **有效期**：不填长期有效；过期后打开会明确提示过期日期；**随时可撤销**，撤销后立刻失效
- **访问计数**：能看到相册被打开过几次
- token 是 32 位随机十六进制，不可枚举；「分享链接」页可查看 / 打开 / 复制 / 撤销全部分享

### 防盗链

「系统设置 → 防盗链」：默认**关闭**（打开后白名单没配全会误伤正常引用，所以交给用户显式开启）。

- 只对**本服务自己提供文件**的端点生效：本地存储的 ```/files/**``` 与缩略图 ```/thumb/**```；
  GitHub / OSS 等后端的直链要在各自控制台或 CDN 上配
- 白名单按域名匹配，**子域自动放行**，本站（同源）永远放行
- **没有 Referer 默认放行**：直接粘贴图片地址、浏览器隐私设置都会没有 Referer，一刀切会挡住正常访客

### 审计日志

「审计日志」页（仅超级管理员）：谁在什么时候做了什么，支持按动作 / 结果 / 关键字（用户名、详情、IP）过滤。

- **保留策略**：`AUDIT_RETENTION_DAYS`（默认 180 天）超期自动清理，应用启动后每 24 小时执行一次；设为 0 表示永久保留
- **导出 CSV**：`GET /api/audit-logs/export` 支持与列表相同的 `keyword / action / success` 筛选，
  带 UTF-8 BOM（Excel 打开中文不乱码），单次最多导出 `AUDIT_EXPORT_MAX_ROWS`（默认 50000）行

记录的是**会产生影响的操作**：登录（成功 / 失败 / 锁定）、上传、移入回收站、恢复、彻底删除、清空回收站、
存储配置增删改、账号增删改与重置密码、系统设置修改、创建 / 撤销分享。读操作不记，免得日志被翻页刷满。
每条含操作者、动作、对象、详情、来源 IP（优先取 ```X-Forwarded-For```）与 User-Agent。

### 登录失败锁定

「系统设置 → 登录安全」：同一账号连续输错密码达到次数（默认 **5** 次）后锁定一段时间（默认 **15** 分钟），
期间**即使密码正确也拒绝登录**。失败与锁定都会写进审计日志。

- 计数在内存里，重启即清空：攻击者拿不到持久的锁，管理员也不用手工解锁
- 计数窗口就是锁定时长：一段时间没有新的失败就重新计数，避免有人每天失败几次把正常用户长期锁在门外

### 分享：打包下载与访问明细

- **打包下载**：相册页有「打包下载全部」按钮；接口 `GET /api/shares/{token}/download`（**公开**，密码相册带 `?password=`）。
  后端**边取边写 zip**：内存里最多只放一张图，几百张也不会把服务端撑爆；单张失败只写进包内失败清单
- **访问明细**：每次打开相册（含打包下载）都会记一条「时间 / 来源 IP / User-Agent」，
  「分享链接」页点「明细」查看最近 200 条。明细表 ```share_view``` 只保留每条分享最近 200 条，防刷

### 元数据导出与回灌（数据备份兜底）

图在云端、清单在 MySQL —— 库一旦出问题就只剩一堆散图。**「系统设置 → 数据备份」**把清单单独留一份：

- **导出**：```GET /api/images/export?format=csv|json```。只导元数据（对象键、访问地址、大小、sha256、宽高、
  存储类型、回收站状态、时间），**不含图片文件本身**；CSV 带 UTF-8 BOM，Excel 直接打开中文不乱码
- **回灌**：```POST /api/images/import-manifest```，按**对象键去重、幂等**（同一份清单重复导入不会产生重复行），
  只补库里没有的记录、**不会重新下载或上传任何文件**；存储配置不存在时回落到该账号第一个可用配置
- 典型场景：换数据库后把清单导回来；误删了记录；想核对云端与库里的存量是否一致

### 存储后端定时体检（凭证过期早知道）

Token 过期、桶被删、网络不通这类问题，与其等用户上传失败才发现，不如定期主动测一遍：

- **每 6 小时**把所有「已启用」的配置真测一遍（```STORAGE_CHECK_ENABLED``` / ```STORAGE_CHECK_INTERVAL_HOURS``` 可配）
- **失败才写审计日志**（动作码 ```STORAGE_CHECK```），成功的不刷屏
- 「存储设置」列表有「健康」列（正常 / 异常 / 未检测，悬停看上次时间与原因），也有「立即体检」按钮手动跑

### 重复图片

「重复图片」页（仅超级管理员）：按内容 sha256 分组，把**完全一样**的多份文件找出来 ——
秒传只能拦住之后的上传，历史数据（多次导入、从别的平台迁移过来）里往往已经有重复。

- 每组标出「保留」的那张（最早上传的，最可能是图库在用的记录），显示可回收的空间
- 「只保留最早一张」/「全部清理」都是**移入回收站**而不是物理删除，误判还能恢复
- 只比对内容完全相同的文件，不做相似图检测（感知哈希有误判风险，宁可漏杀不可错杀）
**保留哪一张可选**（内容都一样，差别只是留哪条记录）：

| 策略 | 说明 |
| --- | --- |
| 最早上传（默认） | id 最小，最可能是图库在用的那条 |
| 最新上传 | id 最大 |
| 最大文件 | size 最大 |

**可按存储后端 / 目录前缀筛选**（与图库同一套语义），接口：

- 列表：`GET /api/images/duplicates?storageConfigId=&directory=`
- 清理：`DELETE /api/images/duplicates?hash=&keep=earliest|latest|largest&storageConfigId=`

### 页面结构抽取（去重）

列表页的头部与分页是重复最多的两块，抽成了共享组件：

| 组件 | 作用 | 已接入 |
| --- | --- | --- |
| `PageHeader.vue` | 标题 + 副标题 + 右侧操作区，统一间距 | 分享链接 / 回收站 / 用户管理 / 审计日志 / 重复图片 |
| `Pager.vue` | 统一分页条（布局、尺寸样式只写一遍） | 审计日志 / 重复图片 |
| `usePager.ts` | 分页状态组合式函数（page/size/total + 翻页回调） | 新页面推荐直接用 |

之前每个页面各写一份 `<h2 class="page-title">` 与 `<el-pagination>`，间距与按钮顺序不一致；
现在新增页面直接复用组件即可。

### 迁移：失败项持久化 + 一键重试

任务列表只在内存里，**服务重启后会清空**（已知设计）。但「哪些图没迁成」不能跟着丢：

- 失败项落到表 `migration_failure`（图 id + 目标配置 + 原因），**重启不丢**
- 「后台任务」面板顶部出现**「失败项」区块**：图片名、失败原因、时间 + 「一键重试」按钮
- 重试 = 把这批失败记录**按原目标**重新提交成一个新的迁移任务（照常后台跑、可取消）；
  重试前先清掉这批记录，仍失败的会重新写入，成功的自然消失
- 接口：`GET /api/images/migrate/failures` 与 `POST /api/images/migrate/retry?toConfigId=`（不传则重试全部）

### CDN 线路（预览 / 下载 / 复制各用哪条）

外网图床（尤其 GitHub）走 CDN 会快很多，所以每个存储配置都能配一组**线路**：

- **内置预设**：按存储类型自动生成，**顺序按国内实测可用性排**。GitHub contents 模式给了
  **gh-proxy.com**、**ghproxy.net**（两个长期运营的公共镜像）、
  **jsDelivr 官方 Cloudflare 节点**（`testingcf.jsdelivr.net`）、**jsDelivr 官方默认**（`cdn.jsdelivr.net`，国内部分地区不可直连）；
  其他后端（OSS / COS / R2 / Kodo / S3）的公网前缀本身就是它的 CDN，所以只有「原始地址」

  > 以下是**在纯国内网络下实测**的结果（同一台机器，取仓库里的一张图）：
  >
  > | 地址 | 结果 |
  > | --- | --- |
  > | `raw.githubusercontent.com`（原始） | ✗ 连不上 |
  > | **`gh-proxy.com`** | ✓ 200，2.8s，**刚上传的新图也立即可取** |
  > | **`ghproxy.net`** | ✓ 200，2.0s，**刚上传的新图也立即可取** |
  > | `testingcf.jsdelivr.net` | △ 时通时不通（还依赖 CDN 缓存，新图可能取不到） |
  > | `cdn.jsdelivr.net` / `fastly.` / `gcore.` | ✗ 连不上或 301 回源到被墙的 raw |
  > | `raw.githack.com`、`ghproxy.cc`、`gh.llkk.cc`、`hub.gitmirror.com` 等 | ✗ 连不上 |
  >
  > 镜像站是社区维护的公共资源，**域名可能变更或限速**；不确定时用页面上的「测速」按你当前的网络挑一条，
  > 或者用「自定义 CDN」填你自己的加速域名（最稳）
- **自定义线路**：名称 + 地址前缀，前缀里可以用 `{owner}` / `{repo}` / `{branch}` 占位符
- **三个用途各选一条默认**：预览 / 下载 / 复制可以分别指定走哪条线路，互不影响。
  默认全部是**原始地址**（保持原有行为）——jsDelivr 这类 CDN 有缓存，刚上传的图片可能一时取不到，
  是否启用交给你决定
- **连通性与延时**：CDN 管理页和「选择线路」弹窗里都有延时列，
  点「测速 / 全部测速」会用浏览器的 `HEAD`（no-cors）请求实测**本机到该线路的往返耗时**，
  连不上显示「不可达」。注意这是网络可达性：对方返回 403/404 也算「有回应」，
  所以延时正常不代表这个地址一定能取到图（例如私有仓库的 CDN 地址）
- 入口：**存储设置 → 某个配置的「CDN」按钮**（仅超级管理员）

服务端会按三个默认把地址解析好后随图片一起返回（`previewUrl` / `downloadUrl` / `copyUrl`），
所以图库缩略图、**大图预览**、复制、下载用的都是对应线路，前端不需要自己拼。

> **碰到「缩略图正常、点开大图预览却加载失败」？** 通常是这两个原因：
>
> 1. **缩略图有本地缓存、大图预览是实时拉取**：缩略图走浏览器 IndexedDB 缓存（见「图片缓存」一节），
>    缓存命中时哪怕 CDN 挂了也照样显示；而大图预览每次都要现场请求。
>    所以换 CDN 后如果预览打不开，先用「测速」确认那条线路是不是真的通（看延时列 / 「全部测速」）。
> 2. **回收站里的图片地址是按 `_trash/` 下的真实位置算的**：软删除会把仓库文件搬进回收站目录，
>    它的预览 / 下载地址也同步换成 `_trash/...`，否则就会指着一个早就搬走的旧路径而 404。

### 选择复制 / 下载哪种链接

图库卡片（概览网格同理）上的 **下载 / 直链 / MD** 都会先弹出「选择线路」：

- 列出**原始地址 + 各条 CDN + 原站代理下载**，每条都带**连通性与延时**，可以现场重新测速
- 每行可以直接「复制 / MD」，也可以选中后点底部的「复制选中链接 / 复制选中 Markdown / 下载选中线路」
- 默认项自动选中；「原站代理下载」走服务端取回后回传，适合私有仓库 / 私有桶，或者 CDN 都连不上时的兜底
- 选 CDN 直链下载时，如果该线路没开 CORS，浏览器读不到内容，会自动退化成在新标签页打开并给出提示

### 回收站（逻辑删除 + 物理删除）

删除分两步，避免误删就永久丢图。入口是**左侧菜单的「回收站」**（仅超级管理员）。

**1. 图库里删除 = 移入回收站（逻辑删除，仓库也一起搬）**

- 数据库：打上删除标记（`image_file.deleted=1` + `deleted_at`），图库列表、目录树、统计、详情、下载都不再包含它
- 仓库：把文件从图库目录**搬到独立的回收站目录**（默认 `_trash/`，即 `api/images/2026/10/13/001/x.png`
  → `_trash/api/images/2026/10/13/001/x.png`），原图库目录因此真正"干净"了
- 搬运复用仓库目录整理那套**引用式搬移**（`GithubTreeMover`）：新 tree 直接引用原有 blob 的 SHA，
  **不下载、不上传、不产生重复文件**，一次搬运只多一个提交
- 记录里会存下 `trash_key`（文件在回收站目录里的位置），回收站页面直接显示「已移入回收站目录 / 原地保留」
- **只有 GitHub 的 contents 模式支持这种同仓库搬移**；S3 / Release 附件等没有这个概念，
  这些后端退化为「只打数据库标记，文件原地保留」，在回收站列表里会标注「原地保留」

**2. 回收站里再删 = 物理彻底删除**

- 从它实际所在的位置（`trash_key`，没搬过就是原键）删掉云端对象，再删本地记录，不可恢复
- 云端删除失败只记警告，不会留下"本地没了、云端还在"的孤儿文件

**其他**

- 回收站页面支持按文件名/对象键搜索、批量**恢复**、批量**彻底删除**、**清空回收站**；每行也有单张的「恢复 / 彻底删除」
- **恢复**：先把云端文件从 `_trash/` 搬回原位置（同样零流量），全都搬成功了才改数据库，
  不会出现「数据库说恢复了、文件还躺在回收站目录」的错位；搬运是幂等的，失败可以重试
- 回收站目录里的文件不参与「从存储导入」的扫描，不会又被导入回来
- 回收站里的图片不参与下载、迁移、秒传（上传相同内容不会复用回收站里的记录）；
  导入扫描也把它们当作已导入，先从回收站恢复即可正常操作
- 回收站目录可以改：`TRASH_PREFIX`（默认 `_trash`，仓库根目录下的相对路径）
- 升级说明：老库启动时会自动补上 `deleted / deleted_at / trash_key` 三列（见 `SchemaMigration`），不需要手工改表

### 图库多选与批量操作

多选是批量下载 / 批量迁移的入口，所以做成了「怎么顺手怎么来」：

- **点卡片就选中**：除了图片本身（点击是预览）和操作按钮，卡片任何位置点一下都能选中 / 取消
- **Shift 连选**：先点一张，再按住 Shift 点另一张，整段按同样的状态批量选中 / 取消（和文件管理器一致）

- **选中后有浮动操作条**：底部会浮出「已选 N 张 / 取消选择 / 下载选中 / 批量迁移 / 删除选中」，
  滚到哪都能直接批量操作，不用再回到顶部找按钮；「删除选中」会先弹确认框，

- **选中态一眼可辨**：卡片加蓝色描边 + 光晕，左上角的选择标记填成实心蓝；悬停时图片轻微放大，右下角提示可点击预览

### 角色与权限

系统只有两个角色，**超级管理员只能通过数据库赋予** —— 没有任何接口能提升角色：

| 角色 | 说明 | 能做什么 |
| --- | --- | --- |
| `SUPER_ADMIN` 超级管理员 | 系统管理员 | 上传、删除、批量迁移、从存储导入、存储配置增删改、账号管理、系统设置，外加普通用户的全部能力 |
| `USER` 普通用户 | 只读账号 | 浏览图库、查看详情与大图预览、下载（单张 + 批量 zip）、维护自己的资料与密码 |

> **普通用户看到的是谁家的图库？** 图片和存储配置在库里都是按账号隔离的，普通用户又不能上传，
> 所以只读账号看到的是**超级管理员的图库**（系统图库）：图库列表、目录树、统计、详情、单张/批量下载都用超级管理员的存储配置取内容。
> 超级管理员则仍然只看自己名下的图片，跟上传 / 迁移 / 导入等写操作保持一致。

- **账号管理**：超级管理员可以在「用户管理」里新建、**编辑昵称 / 邮箱**、启用停用、重置密码、删除账号
  （用户名是登录凭据、角色只能改库，所以这两项不在可编辑范围；超级管理员的账号不能在这里改）
- **账号怎么来**：超级管理员在「用户管理」里新建，新建账号固定是普通用户；
  也可以打开 `REGISTER_ENABLED=true` 允许自助注册（注册出来同样是普通用户，默认关闭）
- **怎么变成超级管理员**：只能改数据库，改完**立即生效**，不用重新登录（每次请求都会回库校验角色与状态）：

  ```sql
  UPDATE sys_user SET role = 'SUPER_ADMIN' WHERE username = 'xxx';
  ```

  降权、禁用同理；账号被禁用或删除后，它手上的 token 立刻失效
- **界面差异**：普通用户看不到「上传 / 存储设置 / 用户管理」菜单，图库里没有「从存储导入 / 批量迁移 / 迁移任务」，
  卡片上也没有「删除」；直接敲 URL 会被路由守卫拦回图库
- **接口差异**：管理类接口对普通用户一律 `403`（「该操作仅超级管理员可用」），
  浏览 / 查看 / 下载接口则两种角色都能用
- **超级管理员账号受保护**：界面上不能改它的状态、重置它的密码、删除它，也不能禁用或删除自己

### 批量迁移

图库里已经保存的图片可以批量搬家 —— 既可以只换目录前缀（同一存储内整理目录），也可以整个搬到另一个存储后端。

- 入口：图库页勾选图片 → **批量迁移**；不勾选则迁移「当前筛选条件下的全部图片」（需要显式确认）
- **没有数量上限**：迁移是后台任务，提交后立刻返回，几千张也不会把 HTTP 请求拖超时
- **后台任务面板**：工具栏的「迁移任务」列出全部任务（来源 → 目标、状态、进度条、成功/失败/跳过、耗时、当前文件），
  进行中的每 2 秒自动刷新，可以随时取消；任务记录存在内存里，服务重启后列表清空（已迁移的图片不受影响）
- **同仓库换目录自动走「引用式搬移」**：源和目标指向同一个 GitHub 仓库时，不下载也不上传，
  直接让新 tree 引用文件原有的 blob，顺带删掉旧路径 —— 实测 5 个文件只要 3 次 API 调用（tree + commit + 移动引用），
  而老路要 15 次（5 下载 + 5 上传 + 5 删除），而且不会产生重复文件。跨仓库 / 跨云时仍走原有的下载上传路径
- **文件级并发**：每张图要「下载 + 上传」两次网络往返，串行会慢得离谱。并发数由 `MIGRATE_CONCURRENCY` 控制（默认 6）
- **限流重试**：撞上 403 / 429 / 5xx / 超时会退避重试（`MIGRATE_RETRY_TIMES`，默认 2 次），而不是直接判失败
- **命名方式是两个独立开关**：「保留原目录结构」和「保留原文件名」可以任意组合

  | 保留目录 | 保留文件名 | 目标对象键形如 |
  | --- | --- | --- |
  | 否 | 否 | `目标前缀/日期/分片/随机名.png` |
  | 是 | 否 | `目标前缀/源目录结构/随机名.png` |
  | 否 | 是 | `目标前缀/日期/分片/原文件名.png` |
  | 是 | 是 | `目标前缀/源目录结构/原文件名.png` |

  勾选「保留原文件名」时如果重名，会自动追加 `-1`、`-2` 序号，不会覆盖已有文件。
  迁移弹窗里会实时显示目标对象键的样子，不用靠猜
- 可选「迁移成功后删除源文件」（仅跨存储时删；同存储同路径会被跳过，不会误删）
- 支持取消；单张失败只记入错误列表，不影响其余图片，结束时给出 `SUCCESS / PARTIAL / FAILED`
- **失败原因按原因归并**：同一种原因的合并成一条（URL 等易变部分会归一化成 `<地址>`），
  给出完整失败张数 + 最多 10 个示例文件名，按失败数量从多到少排列；不同原因都会列出来，不再有条数上限

本地桩实测（1200 张，S3 桶 → S3 桶，含下载 + 上传 + 改库）：

| 并发数 | 耗时 | 单张 |
| --- | --- | --- |
| 1（串行） | 12.8 秒 | 10.7 ms |
| 8 | **3.7 秒** | **3.0 ms** |

并发 8 时约 **3.5 倍**提速。没有跑到 8 倍是因为每张图还要写一次数据库、且对象键分配需要串行 —— 这两处是剩下的瓶颈。
真实 GitHub 上瓶颈会变成网络往返，并发收益更明显；但要注意 5000 请求/小时的配额。

> 换成真实的 GitHub 时要注意 API 配额：认证用户 5000 请求/小时，而每张图片要「下载 + 上传」两次调用，
> 也就是大约 2500 张/小时。超了会开始失败（任务不会中断，失败的会列在错误里），可以过一小时再对失败的重新跑一次。

## 七、源码方式启动（开发用）

```powershell
.start.cmd                      # 后端 + Vite 前端（http://localhost:5173）
.start.cmd -Action status
.start.cmd -Action stop
.start.cmd -Database h2         # 强制内存库
.start.cmd -Target desktop      # Tauri 桌面端
.start.cmd -Rebuild             # 强制重新编译后端
.start.cmd -BackendPort 8081 -WebPort 5174   # 临时改端口
```

**端口怎么改**（不用改脚本，脚本里的 8080 / 5173 只是默认值）：

方式一：命令行参数（最临时）

```powershell
.\start.cmd -BackendPort 8081 -WebPort 5174
./start.sh  -BackendPort 8081 -WebPort 5174
```

方式二：写进 `config/local.env`（长期生效，start 脚本会自动读）

```ini
BACKEND_PORT=8081
WEB_PORT=5174
```

优先级：**命令行参数 / 环境变量 > `config/local.env` > 默认 8080 / 5173**。
脚本会把后端端口通过 `SERVER_PORT` 传给 Spring Boot、把前端端口传给 Vite，
Vite 的 `/api` 代理目标也跟着 `BACKEND_PORT` 走，所以只改一处即可，
状态 / 停止 / 浏览器打开的地址都会用新端口。

> 桌面端（Tauri）的 `devUrl` 固定写在 `web/src-tauri/tauri.conf.json` 里，
> 改 `WEB_PORT` 后如果要调试桌面端，把那里的 `http://localhost:5173` 一起改掉；
> 打包后的单进程模式只有一个端口（后端那个）。

## 十一、安全设计

- 密码 BCrypt，登录态为无状态 JWT。
- **两种角色在服务端强制校验**：管理类接口（上传 / 删除 / 迁移 / 导入 / 存储配置 / 账号管理）在 Spring Security 里按路径限定为超级管理员，
  前端隐藏菜单只是顺手的体验，越权请求一定会被拒。
- **角色与状态以数据库为准**：每次请求都会回库确认账号存在、未禁用并取最新角色，
  所以改库提权 / 降权 / 禁用都是即时生效，旧 token 也不会继续放行。
- 存储密钥 AES-256-GCM 加密入库，接口回显统一 ```******```，编辑时保留占位符即不修改。
- 存储配置按 ```user_id``` 隔离，越权返回 403。
- 上传做扩展名白名单 + 大小限制校验。
